# 自动化测试架构与开发约定

## 测试先行

遵守 AGENTS.md 的 RED → GREEN → REFACTOR。需求验收条件先于实现，测试失败必须来自目标行为缺失；修复先复现错误。记录真实执行结果，不以事后补测冒充测试先行。

## 分层架构

| 层级 | 职责 | 接入时机 |
|---|---|---|
| 规范检查 tests/governance | 规则、检查入口、配置完整性 | 当前已接入 |
| 单元测试 | 业务规则、数据校验、边界和异常 | 首次业务逻辑变更 |
| 集成/接口测试 | 接口契约、鉴权、存储、错误响应及外部服务失败 | 首次加入对应边界 |
| 端到端测试 | 真实浏览器中的关键用户流程及错误恢复 | 首次加入用户界面 |
| 静态检查与构建 | 类型、代码规范、编译及打包 | 选择技术栈时 |

测试目录按所选框架确定，不先引入无用依赖。浏览器测试应验证用户可见结果，关键流程不能全部拦截成模拟成功。测试数据和端口隔离；清理仅针对本次创建的临时资源；不得覆盖本地或生产数据库。

## 统一执行入口

npm run check 先运行规范测试，再依次执行 testing.config.json 的 commands。每项填写 name、command、args、cwd 和 kind；kind 为 test、lint、typecheck 或 build。至少一个真实业务测试命令使用 kind=test。command 是可执行文件名，参数分别放 args，不使用 shell 拼接。cwd 相对项目根目录。

例如采用 Node 内置业务测试时，添加 {"name":"业务单元测试","command":"node","args":["--test","tests/unit"],"cwd":".","kind":"test"}。示例目录尚不存在，不能直接当作已接入。

第一项业务功能必须将 businessTestsRequired 改为 true 并加入真实命令。未配置时 check 显示 BUSINESS TESTS NOT CONFIGURED；check:release 会失败。命令非零退出、启动失败或超时都会导致检查失败。每个命令最长 10 分钟。新增命令必须能在干净环境重现，不能依赖本机运行中的服务。

## 技术栈确定后的接入清单

- 选定测试运行器，锁定依赖版本，补充本机和 CI 的依赖安装步骤。
- 接入单元测试、集成测试、类型检查、lint 和生产构建；有界面时接入浏览器测试及必要的浏览器安装。
- 为关键路径和已发生的问题建立测试；设置合理覆盖率阈值，不把百分比作为正确性保证。
- 配置 CI 测试报告及失败截图/日志的保留，避免上传隐私数据。
- GitHub 托管时配置分支保护，要求 checks 成功才能合并；本地文件不能自行强制远程策略。
- 外部 AI/OCR 等服务先测试超时、无效响应、限流和重试；默认离线替身，真实服务契约测试按环境显式启用。

CI 当前只需要 Node，无业务依赖。check:release 的成功只代表已配置检查通过，人工仍需核对验收条件和部署要求。
